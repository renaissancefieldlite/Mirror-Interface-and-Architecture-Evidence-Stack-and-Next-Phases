## Hard Rule: No Toy Data

The primary evidence rule is:

```text
NO TOY DATA
```

Scaffolds, local engines, generated examples, route maps, and schema drafts can
prepare a lane. They do not close a lane.

A lane earns evidence language only when it is tied to captured, sourced,
observed, measured, or artifact-backed data with controls or a named next
control gate.

Do not use defensive filler about whether the work is real. The point is
traceability, controls, and claim tier.

## Never Do These Things

- Never collapse the architecture into the latest symptom.
- Never answer from one folder view as if it represents the whole repo.
- Never imply a file exists in the user's visible folder unless that exact path
  has been checked.
- Never move, delete, hide, or replace older evidence to make a newer phase
  visible.
- Never conflate `docs`, `artifacts`, `artifacts/validation`, `visuals`, public
  evidence, private raw capture, and runnable code.
- Never push public repo changes without explicit approval after showing scope.
- Never publish private code, raw captures, local device paths, keys, dense
  private exports, or patent-sensitive internals into the public evidence repo.
- Never rewrite the white paper, proof spine, claim spine, or rulebook casually.
- Never treat AI agreement as evidence. The code, captures, artifacts, charts,
  PDFs, manifests, commits, and sourced datasets are the authority.
- Never promote scaffold output as support evidence.
- Never use language that shrinks the architecture into a small app feature,
  pitch decoration, or isolated experiment.
- Never ignore the known-good execution route when a working route exists.
- Never keep the user in the dark during long work. State the exact read,
  exact edit, exact path, and exact next move.

## Required Cross-Gather Before Acting

Before making a repo edit that touches architecture, evidence, public release,
patent support, Phase 12B/12C, B.A.S.I.S., Golden Mirror, Nest lanes, or V7/V8:

1. Check current git state.
2. Locate the relevant files with `rg --files` or `git ls-files`.
3. Identify the surface:
   `docs`, `artifacts`, `artifacts/validation`, `visuals`, private capture,
   code, deck, patent, or product.
4. Read the current spine documents that govern the task:
   `README.md`, `UNIFIED_MIRROR_PROOF_SPINE`, chronological log, companion
   completion matrix, relevant Nest doc, relevant Phase doc.
5. Separate:
   evidence claim, invention claim, product claim, private execution detail,
   public-safe summary, and next gate.
6. State the intended change before editing.
7. Make one narrow change.
8. Show changed paths and diff summary.
9. Commit or push only after explicit approval.
